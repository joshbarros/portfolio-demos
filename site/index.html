02 — Approach

Four rules I do not trade away.

The demo is the easy part. These are the decisions that keep an AI feature from becoming an incident, a surprise invoice, or a support ticket nobody can explain.

01

Correctness you can show

Every system ships with checks a buyer can run: a behaviour eval for the agent, concurrency tests for invoices, cross-tenant tests for RLS, a rollback drill for migrations. “It works on my machine” is not evidence.

02

Permissions in code, not in the prompt

The model proposes language; the application decides what it is allowed to do. Tenant filters live in SQL, tool arguments are validated, secrets are redacted, and actions are audited.

03

Cost is a design constraint

Retrieval, caching, model choice and context size are engineering decisions. I measure tokens and latency before adding another model call, and I write down the trade-off.

04

Honest limits

At-least-once instead of exactly-once. A freeze window instead of zero downtime. Deterministic retrieval instead of magic. If I cannot prove a claim, it does not go on the page.

The tenant filter is a database fact.

In Vaultgate, the application connects as a role that does not own the tables. The policy is forced, and the tenant id comes from the session — never from a query parameter.

A front-end guard can be bypassed by a request. A policy in Postgres cannot. The demo blocks a cross-tenant read and shows the database error, not a friendly toast.

vaultgate / policies.sqlPostgres 16
-- the app role can read only its tenant's rows
alter table documents enable row level security;
alter table documents force row level security;

create policy tenant_isolation on documents
  using (tenant_id = current_setting('app.tenant_id')::uuid)
  with check (tenant_id = current_setting('app.tenant_id')::uuid);

-- sessions set it once; a request cannot override it
